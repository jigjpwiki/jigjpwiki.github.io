# vNext 6 認証基盤のレビュー

この段階はGoogleの認証と招待の基盤。編集者・閲覧者には本人情報とログアウトだけを許可する。既存の管理画面はオーナー向けのまま。CMSの利用開始には後続のフォーム、担当範囲と編集権限、ユーザー管理画面が必要。

## 検証環境の設定

Google CloudでWebアプリケーション種別のOAuthクライアントを作成し、テスト用アカウントを同意画面で許可する。承認済みリダイレクトURIには検証用WorkerのHTTPS originに /auth/google/callback を追加する。GOOGLE_ADMIN_ORIGINには同じoriginを末尾スラッシュなしで設定する。GOOGLE_CLIENT_IDはWorkerの変数、GOOGLE_CLIENT_SECRETはWorkerのSecretとして管理する。既存のGitHub OAuth設定とSESSION_KEYは維持する。

オーナー認証と既存のCSRFヘッダーを利用し、POST /api/members にemail、role（editorまたはviewer）、disabled（boolean）を送る。初回認証の招待有効期間は7日間。承認済みメールは初回にGoogleのsubへ紐づき、同じメールでも別subは拒否される。更新のたびに既存Googleセッションは失効する。招待取消と無効化はdisabled=trueで行う。メール送信は行わない。

## 後続の設計

担当範囲は組織、グループ、コンテンツ区分で判定する。変更前後と参照先の全範囲を検査し、担当外への影響はオーナーのレビューへ送る。範囲の検証をWorkspace保存と提出の両方で行い、公開直前に最新mainで再検証する。

公開にはリポジトリ限定のGitHub Appを候補とする。候補コミットをActionsでビルドして検証し、候補SHAとbase SHAを固定して検証済みの変更だけを昇格する。mainが進んだ場合は再検証か競合解決。ブランチ保護を維持できる昇格方式を導入前に確認する。Pagesのデプロイ成功を確認してから公開済みにする。編集者のメール・Google subをGitHubへ書き込まない。監査には内部IDを使用する。

## 切り戻し

Google設定を無効化すると新規Googleログインを止められる。既存セッションを即座に止める場合はメンバーを無効化するか旧Worker版へ戻す。SQLiteの追加レコードは既存Workspaceと別キー。DOやSESSION_KEYを再作成せず、既存オーナーセッションと下書きを維持する。実環境での導入・切り戻しは未検証。

## 認証・招待の更新

所有者は設定画面の「編集者と招待」から招待・ロール変更・取消・無効化を操作できる。登録上限は100件。招待にはGmailまたは署名済みの組織ドメインとメールドメインが一致するGoogle Workspaceのアドレスを使う。外部メールを登録した個人Googleアカウントは現在のメールボックス所有者を確認できないため拒否する。対応する場合は別のメール所有確認が必要。

認証の動作には GOOGLE_AUTH_ENABLED=true が必要。false への設定変更は新規認証と既存Googleセッションの利用を停止する。Google API通信は各8秒で打ち切り、新規認証開始はWorker全体で毎分60件まで。GitHubオーナーの既存認証とWorkspaceには独立した経路を使う。

編集者画面はログインとログアウトまで。担当範囲、専用フォーム、公開ジョブ、競合解決、履歴・取り消しは引き続き未実装。

## 担当範囲と閲覧

設定画面の編集者を選ぶと事務所・グループ・カテゴリ・直接公開権限を変更できる。保存すると既存セッションは失効する。以前の招待レコードは担当範囲なしとして扱う。閲覧者に直接公開権限は保存されない。

Google利用者の一覧は、同じmain SHAから取得したマスターを用いてサーバーで絞り込む。取得結果はDO内で60秒キャッシュする。マスターは公開リポジトリから読み取り、編集者に渡すのは許可された公開レコードの一覧情報。複数事務所・出演枠・関連レコードを含む対象は、参照を解決できて許可範囲に収まる場合のみ表示する。所属や関連先への手掛かりがない共通楽曲などは、保守的に対象外とする。

変更前後の権限判定は単体検証済み。編集・公開APIには接続していない。編集許可の実装では変更後のマスター全体と、更新によって影響する逆参照も再検査する必要がある。専用フォーム、下書き統合、直接公開、Pagesの反映追跡、履歴・取り消し、verify-productionの拡張は次の作業。

## イベント・グッズの簡易下書き

招待済みGoogle編集者は、担当イベントの登録・基本項目の編集と、単独商品の登録・販売情報の編集を行える。新規登録では検索欄から関連事務所または人物を選ぶ。操作ごとに既存content-planの全マスター検証を使用し、本人の暗号化Workspaceへリビジョン付きで保存する。簡易フォームでは一組の下書きを復元する。公開履歴や複数商品へ波及するキャンペーン商品と複数販売枠は現段階では拒否する。変更元のレコードが変わった場合も保存済み内容を保持して停止する。

全カテゴリの専用フォーム、オーナー向け簡易モード、キャンペーンの追加・編集、競合解決画面、直接公開、Pages反映確認、履歴・取り消し、本番設定検証の拡張は未完了。

簡易CMSは下書きを対象ごとにWorkspaceへ蓄積し、一覧から再開・個別破棄できる。同じ対象の元データが変化した下書きは保持して保存を止める。差分の選択・再適用は未実装。イベントの開始・終了日時（日本時間）、開催形式、配信URL、料金を追加した。既存商品の価格は既存通貨で更新する。出演者編集は残作業。

## 直接公開の検証用設定

Google編集者の直接公開権限に加え、Workerに CMS_PUBLISH_ENABLED=true、CMS_GITHUB_APP_ID、CMS_GITHUB_INSTALLATION_ID と CMS_GITHUB_APP_KEY（PKCS#8 PEMのSecret）を設定する。GitHub Appのインストール先はこのリポジトリだけとし、Contents write と Actions read を付与する。GitHub生成の鍵がPKCS#1の場合は所有者の端末で `openssl pkcs8 -topk8 -nocrypt -in app.pem -out app-pkcs8.pem` で変換し、鍵をリポジトリに保存しない。既存OAuth・DO・SESSION_KEYを維持する。

候補ブランチをpushすると、既存の公開サイト検証ワークフローが候補SHAに対し実行される。候補では配信収集・Pagesデプロイは実行されない。候補の成功と親コミットを確認し、最新mainと一致するときだけ非強制更新する。mainの進行時は既存の3-way変更計画を再計算して再検証する。GitHub側でmainの強制更新は禁止したまま、候補の昇格に必要な権限を専用Appに限定する。現在のrulesetが更新を拒否する環境では公開は利用できず、所有者が既存の承認ルールとの両立を検証するまで有効化しない。

DOのアラームが1分間隔で1件の共有公開処理を進める。ブラウザーが閉じても継続する。公開確定後は一致する提出済み操作だけを下書きから除く。Pagesへの反映は公開サイトのpublished-commit.txt（ビルドしたコミット）で確認する。待機上限は24時間。緊急停止はCMS_PUBLISH_ENABLED=false。送信済みのGitHub更新は取り消されない。権限取消・停止と同時に開始済みの更新については監査と公開状況を確認する。旧版への切戻しでDOや下書きを消さず、公開待ちの処理がある場合は停止と結果確認を先に行う。

公開対応は現時点ではイベントと単独商品の下書きのみ。最終的な同時編集UI、全カテゴリ、履歴一覧と安全な取消、設定検証スクリプト、ブラウザーE2E、実環境のApp・保護ルール・無料枠の検証は残っている。

簡易CMSから人物に紐づく記念日を登録・編集し、既存の公開ジョブに含められる。イベントでは担当人物から出演者を選べる。一覧は種類・名称で絞り込み、登録順と名前順を切り替えられる。VTuber・音楽・歌枠・キャンペーンの編集、オーナー向け簡易モード、公開キューの改善、競合解決・履歴・取り消し、本番設定検証と全体E2Eは未完了。
