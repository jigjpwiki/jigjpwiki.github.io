# Jigdule Admin vNext 7 — CMS Experience Redesign

## 0. 依頼概要

Jigdule Adminの次期バージョンとして、Admin vNext 7を開発してください。

今回の開発では、既存のAdmin vNext 6で構築した認証・共同編集・下書き・公開・競合解決・履歴管理の基盤を維持しながら、管理画面の情報設計、権限管理、UI/UX、編集体験を全面的に刷新します。

単なるCSSの変更や、現行の簡易CMSの装飾改善ではありません。実際に複数人の編集者が日常的に使用する、完成度の高いCMSとして再構築してください。

対象リポジトリ：
https://github.com/jigjpwiki/jigjpwiki.github.io

公開サイト：
https://www.jigdule.jp/

管理画面：
https://jigwiki-admin.jigjpwiki.workers.dev/

デザイン・操作性の主なリファレンス：
- Directus：https://directus.io/
- Linear：https://linear.app/

Directusのコンテンツ管理機能・データ構造の扱いやすさと、Linearの洗練されたUI・情報密度・操作性を組み合わせた管理画面を目指します。

DirectusやLinearそのものを導入するという意味ではありません。現在のシステムを活かし、その設計思想を参考に独自のCMSを開発してください。

---

## 1. 現在のシステムと開発前提

Admin vNext 6はすでに本番環境に導入されています。

以下について、本番環境で動作したことがユーザーから報告されています。

- GitHubオーナー認証
- Google OAuth認証
- Googleアカウントを使用した編集者の招待
- 簡易CMSのデータ取得
- 下書き保存
- GitHub Appによる公開処理
- 公開サイトへの反映

ただし、全カテゴリ・全権限パターン・競合解決・障害復旧・履歴からの取り消しなどの実環境検証が完了しているわけではありません。

関連する既存PR：
- #53：Admin vNext 6
- #54：CMSのデータ取得・認証付き読み取り・並列接続制御
- #55：Cloudflare Workersのfetch互換性修正

これらはマージ済みです。さらにmainが進んでいる可能性があるので、必ず作業開始時点の最新mainを確認してください。

現在の問題点は以下のとおりです。

1. Google編集者はログイン後、専用の簡易CMS画面に分岐する。
2. Google編集者はGitHubオーナーが使用できるVTuber、記念日、グッズなどの独立した管理ページを利用できない。
3. 簡易CMSにすべてのコンテンツが集約されており、情報量が増えると操作しづらい。
4. 新規登録ボタンが横並びで大量に配置されている。
5. 余白・情報階層・ボタン・テーブル・フォームなどのデザインに統一感が不足している。
6. ユーザーごとに担当事務所・グループ・カテゴリを設定する必要があり、管理負担が大きい。
7. 既存の機能と操作導線に、開発段階で追加された複数の方式が混在している。
8. 本番環境で発生するエラーの診断性・無料枠での性能について、引き続き検証が必要。

## 2. 今回の開発における最重要要件

以下を最優先してください。

### A. 管理画面の統合

GitHubオーナーとGoogle編集者が共通のアプリケーションシェル、共通のナビゲーション、共通のコンテンツ管理画面を利用できるようにしてください。

Google編集者専用の簡易CMSという構造を廃止し、通常の管理画面からすべてのコンテンツ管理ページを利用できるようにします。

オーナー用の画面を単純に複製するのではなく、共通コンポーネント・共通フォーム・共通ルーティングを利用してください。

既存の高度な管理機能も失わないようにしてください。

### B. 権限モデルの簡素化

従来のユーザーごとの事務所・グループ・カテゴリ指定を通常運用では不要にします。

招待された編集者は、原則としてすべての事務所・グループ・コンテンツカテゴリを編集できるようにしてください。

今後新しい事務所やグループ、カテゴリが追加された場合も、全範囲を許可された編集者に対して、個別の権限追加作業が発生しない設計にしてください。

### C. UI/UXの全面刷新

DirectusとLinearを参考に、洗練された業務用Webアプリケーションとして設計してください。

現行のHTMLやCSSを絶対に維持する必要はありません。機能・データ整合性・セキュリティを維持できるのであれば、フロントエンドの構造を大幅に再編して構いません。

### D. 本番環境の保全

既存の本番環境、認証情報、編集者アカウント、下書き、公開履歴、Durable Object、固定IDなどを破壊しないでください。

## 3. 権限モデルの再設計

通常の権限モデルは以下の3種類に統一してください。

### Owner（オーナー）

- 全コンテンツの閲覧・編集
- 新規コンテンツ登録
- 下書きの作成・管理
- 公開・公開申請
- 公開履歴の閲覧
- 安全な変更の取り消し
- 編集者・閲覧者の招待
- ユーザーの有効化・無効化
- ロールの変更
- システム設定
- 管理者専用の高度な操作

現在のGitHubオーナー認証を維持してください。

### Editor（編集者）

- 全事務所・グループ・カテゴリのコンテンツ閲覧
- 全コンテンツの編集
- 新規コンテンツ登録
- 自分の下書きの作成・管理
- 変更差分の確認
- 競合の比較・解決
- 直接公開
- 公開状況の確認
- 公開履歴の閲覧
- 安全な変更の取り消しを新しい下書きとして作成

コンテンツ編集に関する機能は、原則としてオーナーと同等にします。

ただし、ユーザー管理、認証情報、システム設定、任意のGitHub操作などの管理者専用機能は利用できません。

### Viewer（閲覧者）

- 全コンテンツの閲覧
- 公開状態の確認
- 許可された公開履歴の閲覧

編集、下書き保存、公開、ユーザー管理はできません。

### 権限設定画面

通常は以下のみで招待できるようにしてください。

- メールアドレス
- ロール（編集者／閲覧者）

編集者の場合、全コンテンツを編集・公開可能とする共通の権限ポリシーを採用します。事務所・グループ・カテゴリのチェックボックスを一つずつ設定する必要はありません。

ただし、既存の権限設定を無条件に破棄したり、既存ユーザーを突然権限昇格させたりしないでください。

既存のスコープ情報を保持し、オーナーが共通権限ポリシーへの切り替えを明示的に確認できるようにしてください。一度切り替えれば、ユーザー単位で再設定する必要がない設計にします。

必要であれば旧スコープ方式を互換性維持・将来の拡張用として内部に残して構いませんが、通常の管理画面では不要な複雑さを見せないでください。

新規登録されるユーザーは共通ポリシーを利用します。

全範囲の権限を、現在登録されている事務所IDの列挙で表現しないでください。将来追加されるコンテンツにも対応できる明示的なポリシーを使用してください。

### セキュリティ要件

フロントエンドでメニューやボタンを隠すだけではなく、サーバー側で各操作の権限を必ず検証してください。

Google編集者を内部的にGitHubオーナーとして偽装したり、既存のownerフラグを単純にtrueにしたりしてはいけません。

以下を区別してください。

- 認証プロバイダー
- ユーザーのロール
- コンテンツ編集可能範囲
- 公開権限
- システム管理権限

既存コードにおけるowner判定・scope判定・directPublish判定をすべて確認し、コンテンツ権限の共通化に伴う影響を調査してください。

既存のGoogleログイン制御、招待制、本人確認、アカウント無効化、セッション失効、CSRF対策は維持してください。

招待されていないGoogleアカウントには利用権限を付与しないでください。

`GOOGLE_AUTH_ENABLED` と `CMS_PUBLISH_ENABLED` のグローバルな緊急停止機能も維持してください。

## 5. デザインコンセプト

### 目指す方向性

DirectusのCMSとしての使いやすさと、LinearのプロフェッショナルなUIを組み合わせます。

キーワード：

- Minimal
- Refined
- Compact
- Functional
- Consistent
- Fast
- Professional

情報密度はある程度高く保ちながら、視線の流れや操作対象が分かりやすい管理画面にしてください。

一般的な生成AIが作るような、巨大なカード、過剰な余白、不要な説明文、装飾的なグラデーションを多用したダッシュボードにはしないでください。

### デザインの基本方針

- ライトモードを基本とする。
- ダークモードにも対応できるトークン設計にする。
- 白・ニュートラルグレーを中心にする。
- ブランドカラーは選択状態、主要操作、必要な強調に限定する。
- 色だけで状態を区別しない。
- 罫線は薄く、必要な場所にだけ使う。
- 角丸は控えめに統一する。
- 影は必要なオーバーレイや浮遊要素に限定する。
- コンテンツ一覧はカードの羅列よりテーブルを優先する。
- 意味のない英語ラベルや装飾文字を追加しない。
- 表示言語は原則日本語とする。
- 日本語の文字量や行間を考慮する。

### デザインシステム

既存のdesign-system.css、app.css、workbench.cssなどの責務を調査し、競合・重複・場当たり的なスタイルを整理してください。

以下のデザイントークンを統一してください。

- 背景色
- サーフェス色
- テキスト色
- ボーダー色
- アクセント色
- 成功・注意・エラー色
- タイポグラフィ
- フォントサイズ
- 行間
- スペーシング
- 角丸
- シャドウ
- コンポーネントの高さ
- Z-index
- モーション

ハードコードされた色・余白・サイズが画面ごとに増殖しないようにしてください。

既存の公開サイトと管理画面のデザインシステムは適切に分離し、管理画面の変更が公開サイトのデザインに影響しないようにしてください。

### アイコン

Lucide Iconsなど、ライセンス上問題のない統一されたアイコンセットを使用してください。

絵文字や文字記号をアイコン代わりに多用しないでください。

推奨するアイコンの意味：

- ダッシュボード：LayoutDashboard
- VTuber：Users
- 事務所：Building2
- グループ：UsersRound
- 記念日：CalendarDays
- イベント：CalendarRange
- 音楽：Music2
- 動画：Video
- 歌枠：MicVocal
- グッズ：Package
- キャンペーン：Megaphone
- 販売情報：ShoppingBag
- 下書き：FilePenLine
- 公開状況：UploadCloud
- 履歴：History
- ユーザー管理：UserRoundCog
- 設定：Settings
- 検索：Search
- フィルター：ListFilter

使用するアイコンは意味と用途を確認し、採用するライブラリに実際に存在するものを使用してください。

必要以上に大量のアイコンライブラリを追加しないでください。

本番のCSPを維持できるよう、アイコンはローカル配信または安全なSVGコンポーネントとして実装してください。外部CDNに依存しないでください。

## 7. レコード詳細・編集フォーム

現行の簡易フォームと高度な管理画面の編集機能を調査し、機能の重複や不足を整理してください。

Google編集者にも通常のカテゴリ別画面から、既存の編集機能を利用できるようにしてください。

現在オーナーだけが利用できる操作についても、コンテンツ編集として安全に許可できるものは、共通の検証済み編集経路に移してください。

単純にオーナー専用APIをGoogleアカウントへ開放してはいけません。

### フォームの共通要素

- 基本情報
- 関連レコード
- URL・外部リンク
- 画像
- 公開・活動状態
- 固定IDなどの読み取り専用情報
- バリデーション
- 変更前後の差分
- 下書き保存
- 公開操作

カテゴリ固有の情報構造に応じて、セクションやタブを設計してください。

### 関連レコードの選択

VTuber、事務所、グループ、楽曲、動画、商品などは、可能な限り検索可能なセレクト・コンボボックスを利用してください。

数百件以上の候補をそのまま通常のselectに並べることは避けてください。

関連レコード選択時には、必要に応じて画像、所属、種類、補助情報などを表示してください。

内部IDをユーザーが手入力する必要がないようにしてください。

### フォーム操作

- 未保存の変更を明示する。
- 保存中・保存済み・保存失敗を区別する。
- 入力エラーは対象フィールドの近くに表示する。
- 保存失敗時に入力内容を失わない。
- 入力途中で画面を離れる場合は必要に応じて確認する。
- 下書き保存と公開を明確に分ける。
- 公開前に実際の変更差分を確認できるようにする。
- フォームから別の関連レコードに移動できるようにする。

複数商品、複数販売枠、歌枠のセットリストなどの編集機能は、既存機能を削らず、操作性を改善してください。

新規登録、追加、並べ替え、関連付け、取り消しなどもデータ構造に応じて適切に設計してください。

## 8. ダッシュボード

ダッシュボードは装飾的な統計カードを大量に表示するページではなく、編集作業を開始するための実用的なワークスペースにしてください。

表示候補：

- 自分の下書き
- 公開待ち・公開中の変更
- 公開失敗・要対応の変更
- 最近編集したコンテンツ
- 最近公開された更新
- コンテンツへのショートカット
- 必要なシステム状態

存在しない情報を推測して表示したり、架空の統計データを表示したりしないでください。

各情報について取得コストを考慮し、必要なデータを必要なタイミングで読み込むようにしてください。

## 9. 下書き・公開状況・履歴

### 下書き

全カテゴリの下書きを横断して確認できる独立したページを用意してください。

表示・操作候補：

- 対象コンテンツ
- 変更内容
- 新規登録／既存更新
- 保存状態
- 最終更新日時
- 競合の有無
- 公開可否
- 個別編集への遷移
- 個別破棄
- 公開対象の選択
- 変更差分の確認

既存のWorkspaceの互換性を維持してください。
