## 発見とレビュー

- `data/youtube.json`の既存IDを再利用。追加探索は公式チャンネルのuploads playlist（既存`youtube_cache.__uploads__`を読み取り専用で再利用）から行う。未知のuploadsだけchannels.list、詳細はvideos.list最大50件ずつ。search.listは使わない。
- タイトル・説明先頭512文字（「毎日/普段/中心に/配信して」等のプロフィール定型行を除外）・説明欄時刻・登録済み動画IDで候補化。「歌」の1文字だけでは検出しない。本文にあるコラボ相手を歌唱者と自動確定しない。所有者の照合はチャンネルIDで行う。
- 「ワンマン振り返り」「新曲ダンスshorts」等も候補になり得る。イベント実施・楽曲種別・実際の歌唱の確定ではない。カテゴリは重複可能。見逃し/誤検出は残るため、キーワードを公開承認に使わない。
- 動画ID、チャンネルID、タレントID、公開/実配信（なければ予約）日時、根拠URL、取得日時、検出方法、説明全文のSHA-256、既存レコードIDを保存。本文全文は保存せず、上限200行の時刻付き短い原文表記だけ保持する。歌詞行は除外する。
- 同一動画IDは1候補。pending/confirmed/rejected/needs_reviewを扱う。実質的な根拠変更ではneeds_reviewと旧ハッシュ/状態/観測日時の履歴を残す。取得時刻だけの変更は承認を失効させない。旧形式からメタデータ付き形式への移行も再確認扱い。
- 部分入力や取得失敗で観測しなかった既存候補は削除/失効させない。videos.listから返らないIDは`not_returned`とだけ記録し、非公開/削除/活動終了を推測しない。登録済みマスターは一切更新しない。

## CLIと再開

```sh
# 直近7日、20チャンネルずつローテーション。通常は88チャンネルを約5日で一巡。
node scripts/discover-media.cjs --mode daily

# 明示期間 [from,to)、対象人物、各種上限。同じstate/期間/対象で再実行して再開。
node scripts/discover-media.cjs --mode backfill \
  --from 2026-10-01T00:00:00Z --to 2026-11-16T00:00:00Z \
  --talents tal-000006,tal-000007,tal-000011 \
  --max-units 30 --max-daily-units 60 --max-videos 200 \
  --max-pages 6 --pages-per-channel 2 --max-channels 3 \
  --state ops/proposals/runtime/backfill.json
```

`--channels`で既存タレントに紐づくチャンネルを指定することも可能。未登録の人物/企業チャンネルは拒否する。バックフィルはfrom/to必須。通常の期間検索はplaylist項目のvideoPublishedAtに基づき、scheduledStartTime期間検索ではない。公開日時順の逆転を考慮し「古い項目があっただけ」で全走査を終了しない。過去期間は多数ページの再開が必要な場合がある。日次は各チャンネル最新50件に限定し、急増・期間外・古い予約枠の完全性を保証しない。

既定上限は1実行60単位/200動画/30ページ/20チャンネル/各5ページ/240秒。日次は各1ページ。ローカル上限の最大は500単位/5000動画/500ページ/200チャンネル/各100ページ/900秒。要求開始前に上限を確認する（通信の20秒タイムアウト分、時間上限を超える可能性あり）。ネットワーク/429/5xxは250/500ms待って最大3試行。403等の認証/クォータ失敗、レスポンス不正は再試行しない。

単一JSONチェックポイントに候補・メタデータキャッシュ・ページのpending IDs・次カーソル・ローテーション・日次予算・健康状態を一括で一時ファイル→rename保存。API要求前に予算消費を保存し、取得済みのページはメタデータ処理完了まで進めない。中断による再取得はあり得るが重複登録しない。期間/人物/モード別のカーソルを分離する。排他lockで同じstateへのローカル同時書き込みを拒否。異常終了のlockはプロセス停止を確認してから削除する。CIキャッシュはJSONのみでlockを保存しない。

成功メタデータは7日、返却されないIDは1日再利用。古いIDも入力/再走査の対象になれば再確認するが、全履歴の可用性を毎日監視するものではない。

### レビューの持ち帰り

1. Actions ArtifactのJSONをダウンロードし、`queue`を取り出して`ops/proposals/review.json`との差分・根拠を確認する。実行stateをローカルruntime下へコピーして再開することもできる。
2. 確認状態を変更したレビュー用JSONをPRで提出する。confirmedは候補としての確認であり、楽曲IDや歌唱事実の公開承認とは別。
3. 次回CLIはGit側のconfirmed/rejectedを**同じkeyかつ同じevidenceHashの場合だけ**既存キャッシュへ反映する。新しい根拠へ古い確認を流用しない。生のレビューJSONを履歴から取り出せる。
4. 公開用JSON/ID台帳への登録案生成・Schema検証・承認PR・ロールバック支援はPR Bで実装する。今回のCLIには自動import/承認/公開経路がない。

## 日次Actions・費用・運用

新規`discover-music.yml`のみ。毎日04:41 JST（遅延し得るGitHub Cron）、main上のみ。手動daily/backfillも可。既存15分の配信ジョブ、concurrency、Pages再試行、Secrets設定は変更しない。取得キーは既存`YOUTUBE_API_KEY` Secret。contents:readのみで、git push/PR自動作成/Pagesデプロイは行わない。

同一ワークフローの実行は直列化。独立キャッシュにチェックポイントを復元し、失敗時もJSONを保存する。結果Artifactは30日保持。キャッシュはGitHubの通常の容量/退去制約があり永続DBではない。消失時はGitの候補キューを基に再探索し、重複はIDで排除する。重要なレビュー結果はPRでGitに残す。候補JSONはPagesには非公開だが、公開リポジトリのGit/Actions Artifact/キャッシュは機密保管庫ではない。Secrets/本文全文/内部個人情報を入れない。

無料の公開リポジトリActions・標準キャッシュ/Artifact範囲を利用し有料サービスなし。APIはchannels.list/playlistItems.list/videos.list各1単位として**再試行込み60単位/実行**。同一stateのPacific日付（DST対応）で**累計60単位/日**が既定。日次予算は再開でも持続する。別stateや他プロセス/GCPプロジェクト全体の予算を拘束するものではない。

参考：[公式quota cost](https://developers.google.com/youtube/v3/determine_quota_cost)。標準10,000単位/日に対して60は0.6%。ただしこのプロジェクトの実際の割当/残量・他アプリ消費はGCP Console権限がなく未確認。既存収集はupcoming検索に最大50 search呼出/日（5,000単位）、uploadsは活動状況で1/6時間、statusは30分である。60単位を追加しても必ず余裕があるとは断定しない。403時は直ちに停止して既存マスターを保持する。クォータ確認後に必要ならmain向けPRで上限を調整する。

`lastAttemptAt`、`lastSuccessAt`、reportのstopReason/errors/requests/dailyEstimatedUnits/incompleteJobsで健康状態と残作業を確認できる。completeは今回のチャンネル/ページバッチが完了した意味で、全履歴完了ではない。lastSuccessAtが2日以上進まない場合はActions履歴・失敗通知とArtifactを確認する。自動stale通知/外部監視は未実装。予算停止は安全な途中終了でジョブ失敗とは区別する。ネットワーク/API失敗はジョブ失敗になる。GitHub Actions標準の失敗通知を利用できる。
